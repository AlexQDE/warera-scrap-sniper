# WarEra Plus architecture

The extension has no runtime dependencies or build step. Node tooling is development-only. Keep page readers separate from pricing models and privileged I/O.

| Layer          | Modules                                                                                                                                                      | Responsibility                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Privileged I/O | `background.js`, `controller.mjs`, `api.mjs`, `flight.mjs`                                                                                                   | Verify senders, protect the key, validate API data, serialize cache writes, share in-flight requests and cooldowns                                  |
| Models         | `quality.mjs`, `cases.mjs`, `ladder.mjs`, `stats.mjs`, `sales.mjs`, `resale.mjs`, `offers.mjs`, `craftboard.mjs`, `similar.mjs`, `observed.mjs`, `items.mjs` | Pure pricing, probability, depth, freshness, fills evidence, stat ranges, the stat-matched value, the craft board, the player's own crafts replayed |
| Lifecycle      | `content.js`, `app.mjs`, `scheduler.mjs`                                                                                                                     | Bootstrap, visibility, SPA discovery, scoped observers, coalesced rendering and cleanup                                                             |
| Presentation   | `panel.mjs`, `equipment.mjs`, `craftdesk.mjs`, `dialogs.mjs`, `casesview.mjs`, `ui.mjs`, `format.mjs`, `content.css`                                         | The bar, the row lines, the three sections, the case strip; escape strings, preserve keyboard focus, avoid unchanged DOM writes                     |
| DOM adapter    | `dom.mjs`                                                                                                                                                    | Read the game's current markup; cache per-row reads; fail closed when an item, price or stat is ambiguous                                           |
| Preferences    | `settings.mjs`, `popup.js`                                                                                                                                   | Whitelisted public preferences; trusted popup handles key entry                                                                                     |

`craft.mjs` and `craftdata.mjs` (the 1.6–1.8 desk maths: EV over outcomes, break-even ceilings, acquisition, recipe overrides) stay in the tree, typed and tested, but nothing renders them since 2.0.0.

## Data contracts

`parseBook` validates both order sides, aggregates duplicate price levels and sorts bids descending / asks ascending. A depth quote requires the entire requested quantity. An empty side is valid data but cannot fund a nonzero quote. The API's returned order count reaching its cap is explicitly tracked. Observed liquidity is neither reserved nor guaranteed to remain available.

The history store (`hist:<userId>:meta` and one `hist:<userId>:<YYYY-MM>` chunk a month, `controller.readHistory`) is not a cache: every transaction of the player's since the start of the profile, the six item-related types in one walk (`api.HISTORY_TYPES`, `fetchHistoryPage`, rows reduced by `api.reduceRow` to short keys), merged by transaction id. A step polls from the newest row down to the first one in `meta.top` (the newest 300 ids) when `POLL_MS` (60 s; `FAST_POLL_MS`, 15 s, while a game dialog is open; at once when forced) has passed, walks a gap left by a poll that met nothing it held, then reads `BACKFILL_PAGES` (8) more pages from `meta.cursor` until the start of the profile; every page is stored as it arrives, so a step cut short loses nothing. `meta.averages` accumulates the game's daily prices of scraps, steel, the cases and the resources wooden cases gave (the game serves 30 days; each read is kept). The store survives a key change, the key-rejected purge and `cleanup()`; a version change (`HIST_VERSION`) re-reads it, and would lose the craft picks written on the rows (below), so do not raise it lightly. `ledgerView` replays it in the worker (memoised per revision and steel mode) and answers the page with the windows' results, one page of the window's pieces (`LEDGER_PAGE`, 50, newest first, all or one source's, with the counts per source), the last craft and opening, and the codes whose sales would price the held pieces; the page never receives the rows. `unlimitedStorage` is required: one account was 4.9 MB after eight months.

**Sniper crafts** (3.6.0). A craft with its slot chosen burns twice the steel and the feed does not say which way a craft was made. The page reports each press of the game's CRAFT button (`dialogs.createDialogs` observes it; chosen or random by the button's label, the slot by its marked tile) as `craftPick` with the page's clock; the worker keeps the presses under `hist:<userId>:picks` (`PICKS_KEPT`), and every history step (`bakePicks`) ties them to the craft rows they made (`observed.matchPicks`: the offset between the page's clock and the server's is the gap most press-craft pairs agree on within a second; then each craft takes the closest unmatched press of its tier within 20 s) and writes the pick on the row (`p`: `c` chosen, `r` random), where it stays; a press no craft answered by a poll 15 minutes on is dropped. `observed.craftModes` then charges each craft: the setting (`craftSteelMode` random or chosen) forces one way; else the row's `p`; else a streak of the tier's crafts giving the same slot (`CHOSEN_STREAK`: 6 weapons, 5 of one armour piece) is taken for chosen; else random.

Cache schema 2 includes an ISO `at` timestamp. Averages (`avg`, `gameStat.getEquipmentAvgByCode` for the 36 gear codes, one batched read) additionally carry per-item `times` and `failures`: a failed item keeps its previous value and timestamp, is excluded from fresh estimates, and does not refresh the whole cache timestamp. A zero average means no historical price, not a zero-valued item.

Equipment TTL is configurable (10–600 seconds, default 30). Case and resource books use 60 seconds, an item's sales 300 seconds (7 days, ten pages at most), averages 600 seconds, the player's feed 180 seconds. Old quotes can be displayed with stale status but cannot generate tags. A failed manual refresh also pauses tags until a usable fresh result arrives.

**The value of a row** (`equipment.valueOf` over `similar.similarValue`): with the item's sales read (`similar.windowFills`: `resale.comparableFills` cut to `WINDOW_HOURS` = 168, no durability filter since listings are always at 100%, worked out once a minute per read and shared by every row, the Ledger and the sell form), each sale's stats are measured against the piece's as a share of every stat's roll range (`stats.STAT_RANGES`, `statDistance`: the largest share wins, so a sniper's crit, 4 wide, weighs as much as its attack, 29 wide). The value is the median of the sales within `SAME_DISTANCE` (0.1) when there are `MIN_SAME` (3), else within `SIMILAR_DISTANCE` (0.25) when there are `MIN_SIMILAR` (5), both `matched`, each sale first brought to the piece's own stats by `similar.statSlopes` (what each stat is worth on that item's market: a Theil-Sen slope of log price per share of the stat's range over pairs of the newest 200 sales sold within 48 h of each other with the other stat within 30%, backfitted for a weapon's two stats, clamped to 0..2, 0 below 40 pairs; `scripts/backtest-prices.mjs` measures it on synthetic markets); else of the item when there are `MIN_ITEM` (5), unmatched and never adjusted; the matched sales' stat span, price range and median listing-to-sale wait travel with it. Without sales, the game's average for the code from the `avg` cache, unmatched, labelled stale past its TTL. The piece's stats come off the row: `offers.readStats` takes the last `NN%` before the price as the durability and every number before it as a stat (live rows: a weapon prints attack, crit, durability; an armour piece its one stat and the durability), and `similar.rowSkills` keys them as the fills carry them. The verdicts: `dom.verdict` for the scrap side (SNIPE at `minMarginPct`, NEAR MISS below a negative threshold), FLIP when the value is `matched` and `(value − price) / price ≥ flipPct / 100` and the scraps do not hit, PASS otherwise; READING / NO QUOTE / STALE suppress every tag. `similar.listedPeers` counts the other rows of the same code within `SAME_DISTANCE` and their cheapest price. The percentile of the price among the matched sales needs eight (`resale.percentileRank`); the stat rank among listed peers needs eight too (`offers.statRanks`).

**The v0.27 auction house** (3.7.0, read on the dev server; `docs/GAME-FACTS.md` §11). `dom.auctionRows` reads auction cards beside `dom.offerRows`' v0.26 rows (a page shows one or the other) and gives the same row shape plus `kind: "auction"`, the bid button and its amount, the start (or current bid), the max and the countdown. A card is the first ancestor of a priced button that shows an item, holding exactly two priced buttons (buy now, then bid); it is read by position over `dom.auctionTokens` (text nodes, buttons left out, split decimals, percents and countdown units joined), never by its translated labels, and its stats by `offers.readStatBlock`. The buttons' amounts include the buyer's tax and the card's prices do not: `dom.auctionTax` checks the one against the other with the notice's rate (else takes the card's own), and a card that fails gets no verdict. `equipment.render` judges buying now as it judged an offer (SNIPE, FLIP) and adds `bid`: the next bid pays by scraps or by matched sales, with the ceiling before tax. `sellform.findAuctionForm` / `readAuctionForm` / `renderAuctionHint` and `pricing.suggestAuction` (the game's estimate: `pricing.estimatedValue`) price the Start an auction form for one piece. `npm run build:dev` (`scripts/build-dev.mjs`) copies the extension to `dist/dev`, pointed at dev.warera.io and apidev.warera.io; each substitution must match exactly once, and the store manifest does not change.

**Offer dimensions** (`offers.mjs`): `readStats` parses durability (`NN%`, the first such line) and the stat value from a row's visible lines, excluding the price line before BUY, and names its reason when it fails; `summarizeOffers` counts readable rows without reference to quotes or sales.

**The craft board** (`craftboard.mjs`): `craftCost` walks the tier's scraps and the steel fee through the asks (`quality.quote`; no price past the observed depth, the missing input named). `tierBoard` gives one row per tier: the random cost (`CRAFT_STEEL`) and the chosen-slot cost (doubled), the six slots with their odds (`RANDOM_SLOT_ODDS`) and averages, the random EV (withheld while any slot lacks an average), the best covered slot, the ROI either way, the scraps' bid value when scrapped and the loss a random craft takes when its roll is scrapped at once. `bestTier` ranks by random ROI, else by chosen ROI.

**The player's pieces** (`observed.mjs`): `replayHistory` makes one piece of every craft (cost = the recipe at the craft day's prices), every case opening with a piece (cost = the case's price that day: what it would have sold for), every market row where the player is the buyer (cost = the money paid) and every battle drop (cost 0); a wooden case's resource is valued apart. Prices come from `makePricer`: the game's daily average, else the median unit price of the player's own trades that day, else the nearest day on record (`approx`). A sale or dismantle is the fate of the latest unfated acquisition with its item id; a sale gives the piece a new id, so failing that it is the acquisition of the same code and stats closest to the row's `la` (when the seller got the piece) within `ACQUIRED_WITHIN_MS`, else the latest one of the same code and stats before it (a relisted piece's `la` moves to when it came back). A fate with no acquisition becomes a piece of source "unknown" with no cost (2 of 11,780 on one account). `outcome` sums a set of pieces (cost, proceeds, held value, realized, estimated incl. held); `windowView` splits a window by source, case and crafted tier, and counts the window's money by the day pieces went. The ledger reads the player id from the settings, else from the page's own-profile links (`dom.ownUserId`), on every page, and never shows a view for another id.

**Game facts** (`ladder.mjs`): the scrap ladder, the dismantle yield, the craft steel fee (`CRAFT_STEEL`, doubled for a chosen slot) and the random craft's slot odds, each with its provenance; `docs/GAME-FACTS.md` is the written record every number here points to.

**Preferences** (`settings.mjs`): `minMarginPct`, `flipPct`, `intervalSec`, `panel` (`none` | `market` | `craft` | `ledger`: the section open under the bar), `casesCollapsed`, `roundTrip`, the module toggles, `sellFrom`, `userId`, `craftSteelMode` (`auto` | `random` | `chosen`; schema 6 reads a `random` saved before it as `auto`, the old default every save wrote; a save from the settings page carries `CHOICE_FIELDS` under the current schema), `ledgerMode`. Unknown keys, including the 1.x `collapsed`, `craftCollapsed`, `craftBatch`, `craftTargetPct`, `taxPct` and `craftRecipes`, are dropped on the next save. The 1.x `craftLedger` storage entry is neither read nor removed.

## Request and account lifecycle

Single-flight identity is resource + item + account generation, never the force flag. All callers share the same active read, including manual refresh. Writes and key changes are serialized. An old-key response cannot overwrite a new account's cache. Display preference revisions do not invalidate account data; a changed key or an explicit re-save after rejection increments `authRevision` and clears account caches.

An item's sales cache whose fills carry their transaction ids is brought up to date rather than read again: `api.fetchSales` with `known` stops at the first sale held (usually one page instead of `SALES_PAGES`, ten), and the worker merges what is new onto what it held inside the week.

Without a key (3.4.0) the book, the case books and the averages are read keyless (no header; the keyless bucket is then the expected answer, not a rejection), while sales and the history answer `needs-key` without a request, and the page (`state.hasKey`) never asks for them: the market sales line, the Ledger, the dialogs and the picker say they need the key. The worker remembers a rejected key across worker restarts. Saving a key explicitly clears rejection, including when the user re-saves the same corrected/renewed key. A server 429 hold is global and persisted in session storage. Transient resource failures get bounded exponential backoff with jitter; forced refresh does not bypass it.

Keys are stored in extension-local storage restricted to trusted extension contexts. Content messages only receive public preferences and `hasKey`/rejection state. Requests omit credentials, disable HTTP caching and refuse redirects. Errors redact the supplied key before returning to the page. This is local browser storage, not an encrypted password vault.

The content side keeps the fills of the last twelve items it read (`salesByCode`) so rows of other items keep their value evidence; fills freshness, errors and the read in flight are tracked per item. Fills reads are single-flight per tab: one asked for while another item's read is in flight is kept, with whether it was forced, and runs when that read finishes; reads kept while the tab was hidden run when it becomes visible again. A failed fills read is not asked again for 15 s. The rows ask for every item on the page, the grid's selected item first; the Ledger asks for the held pieces' items (eight at most) on every render, a fresh read returning at once. `SALES_CODES_KEPT` is 36, so no item on the page is evicted.

## UI lifecycle and performance

The content script runs at `document_start`, so the app is up before the game draws its market. Scans are scheduled by `scheduler.mjs`: after a quiet spell before the next paint (`requestAnimationFrame`), so rows the game has just drawn get their lines in the frame they first show in; while the page keeps changing at most once every 100 ms. For 15 s after the start or an address change (a popstate, the five-second tick), and 3 s after any click, a discovery observer on the whole document schedules a scan for any node the game adds, so what it draws late (the offer list after its own read, a dialog) is found at once; it disconnects itself. An offer row's line keeps one width (`27em`, an ellipsis past it; open Details take the row) so the game's price and BUY never move as its words change; the first frame says READING. `scripts/jitter.mjs` measures the settling time, the rewrites and the layout shifts.

API reads stop while the tab is hidden, and so does rendering: a setting saved from a hidden tab shows once the tab is visible. The scrap book and the averages are read whenever the rows are on screen; the steel book with the Craft tab open; the player's history is stepped on every 5-second tick of any game page where the player id is known (the worker decides whether a poll or a backfill page is due), so a sale shows in the head within a minute.

**The game's dialogs** (`dialogs.mjs`): `findDialog` recognises the case window (an OPEN button and the odds it prints; `caseFromOdds` tells the case by its common share) and the craft window ("CRAFT ITEMS" and a CRAFT button; `craftTier` reads the heading after the six tier tiles), read live on 2026-10-08. The panel goes before the box holding both open buttons, or before the craft button. A capturing click listener observes a press of the game's own OPEN or CRAFT button (never prevents or makes one) and asks for a forced history step 2.5 s and 7 s later, with fast polling for two minutes. No notification, sound or badge: a number that updates is display, a ping is not. Rendering uses scoped mutation roots, filters extension-owned mutations and coalesces native mutation bursts with a 100 ms scheduler. Unchanged markup is not written again, and an age label ("12s ago") changing by itself does not count as changed markup; `clock()` keeps ages current. A rewrite keeps keyboard focus on the same control, identified by its action or field together with the code, id, type, tab, tier or window it carries. The bar (`panel.mountBar`) sits before the market's tax notice, else before the section holding the item grid (`dom.marketAnchor`), and stays put while only the extension's own nodes sit between it and its anchor; its head is `app.mjs`'s, its body is rendered by `equipment.renderMarket` or `craftdesk.render` for the open tab, or hidden.

Offer scans are scoped: rows are looked for inside the list container found by the previous scan, with a full-document scan when that container is gone, finds nothing, or every 30 s. `createRowCache` keeps each row's parsed lines, price, frame and border colour; the layout-forcing `innerText` is read again only when the row's native text changes, and the frame colour only on a full scan (a new cache epoch), so a theme change is still picked up. Per-row annotation HTML is rebuilt only when its memo key (tag, quote time, thresholds, fills snapshot, value, stat rank, Details state) changes. Only the Details button and the Details text catch a click; the rest of the line is the row's, in the click handler as in the stylesheet.

A light five-second heartbeat checks preference revisions, URL changes and freshness transitions. A 30-second discovery fallback catches replaced SPA containers or newly opened dialogs outside observed roots. This deliberately avoids patching the game's history or global JavaScript.

Dispose disconnects the observer, cancels timers, removes extension UI (the bar, the row lines, the case strip, the trip line) and restores picker visibility. The content bootstrap handles ordinary unload; persisted back/forward-cache pages keep their instance. A second content-script injection is stopped by the original `window.__scrapSniper` marker.

## Tests and extension safety

Run `npm run check`; `npm run package` builds the store zip (the reached scripts only, no tests, reproducible). Unit tests cover models (the stat-matched value and its 7-day window, the live row layouts, the feed walk's stops and the store's merge and coverage, the pieces' replay and the day's result, the craft board, the feed walk and its cutoffs, the replay, the resale thresholds, depth), malformed envelopes, pagination, missing headers, escaped text. Controller tests use injected storage, fetch and clock for races, cooldowns and the feed cache. jsdom tests cover SPA navigation, mutation storms, hidden tabs, settings updates, duplicate mounting, the Details control, the bar's tabs, the craft board, the ledger and cleanup. They do not prove real Chrome layout, extension permission behavior, live API compatibility or the live page's row text; `scripts/screenshots.mjs` renders the synthetic fixture in headless Chromium for screenshots and the loader benchmark.

The strict JS/TypeScript check covers `quality`, `settings`, `format`, `items`, `ladder`, `stats`, `resale`, `offers`, `craft`, `craftdata`, `craftboard`, `similar` and `observed`. Expand this list as additional modules gain types; do not represent it as whole-project TypeScript coverage. ESLint checks all extension code and scripts. The manifest validator walks local module imports and ensures privileged modules are not web-accessible.

When adding a feature, start with a pure model and a fixture, add a controller resource only if necessary, then mount it through `app.mjs`. Never add the API key to the content state, patch the page's `fetch`, or call a transaction mutation endpoint.

# WarEra Plus architecture

The extension has no runtime dependencies or build step. Node tooling is development-only. Keep page readers separate from pricing models and privileged I/O.

| Layer          | Modules                                                                                                                                                      | Responsibility                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Privileged I/O | `background.js`, `controller.mjs`, `api.mjs`, `flight.mjs`                                                                                                   | Verify senders, protect the key, validate API data, serialize cache writes, share in-flight requests and cooldowns                                  |
| Models         | `quality.mjs`, `cases.mjs`, `ladder.mjs`, `stats.mjs`, `sales.mjs`, `resale.mjs`, `offers.mjs`, `craftboard.mjs`, `similar.mjs`, `observed.mjs`, `items.mjs` | Pure pricing, probability, depth, freshness, fills evidence, stat ranges, the stat-matched value, the craft board, the player's own crafts replayed |
| Lifecycle      | `content.js`, `app.mjs`, `scheduler.mjs`                                                                                                                     | Bootstrap, visibility, SPA discovery, scoped observers, coalesced rendering and cleanup                                                             |
| Presentation   | `panel.mjs`, `equipment.mjs`, `craftdesk.mjs`, `casesview.mjs`, `ui.mjs`, `format.mjs`, `content.css`                                                        | The bar, the row lines, the three sections, the case strip; escape strings, preserve keyboard focus, avoid unchanged DOM writes                     |
| DOM adapter    | `dom.mjs`                                                                                                                                                    | Read the game's current markup; cache per-row reads; fail closed when an item, price or stat is ambiguous                                           |
| Preferences    | `settings.mjs`, `popup.js`                                                                                                                                   | Whitelisted public preferences; trusted popup handles key entry                                                                                     |

`craft.mjs` and `craftdata.mjs` (the 1.6–1.8 desk maths: EV over outcomes, break-even ceilings, acquisition, recipe overrides) stay in the tree, typed and tested, but nothing renders them since 2.0.0.

## Data contracts

`parseBook` validates both order sides, aggregates duplicate price levels and sorts bids descending / asks ascending. A depth quote requires the entire requested quantity. An empty side is valid data but cannot fund a nonzero quote. The API's returned order count reaching its cap is explicitly tracked. Observed liquidity is neither reserved nor guaranteed to remain available.

The feed store (`feed:<userId>`, `controller.readFeed`) is not a cache: the player's own crafts, market rows (both sides) and dismantles merged by transaction id, `FEED_DAYS` (30) and `FEED_ROWS` (3,000) a feed, with the daily input averages (refreshed every ten minutes) and the username. The first read backfills 7 days (`FEED_PAGES.backfill`); every later read polls each feed newest first until it meets one of the `FEED_KNOWN` newest ids it holds, a row past the window, the end of the feed or `FEED_PAGES.poll`. `covered` says per feed since when the record is complete (the backfill's cutoff, else its oldest row; rows pruned past the window or the cap move it forward); `holes` says which feed's last walk hit its cap. The store is keyed by the id the page shows, survives a key change and the key-rejected purge, and is dropped by `cleanup()` only when older than the window or of another `FEED_VERSION`. `TTL.feed` is 60 seconds.

Cache schema 2 includes an ISO `at` timestamp. Averages (`avg`, `gameStat.getEquipmentAvgByCode` for the 36 gear codes, one batched read) additionally carry per-item `times` and `failures`: a failed item keeps its previous value and timestamp, is excluded from fresh estimates, and does not refresh the whole cache timestamp. A zero average means no historical price, not a zero-valued item.

Equipment TTL is configurable (10–600 seconds, default 30). Case and resource books use 60 seconds, an item's sales 300 seconds (7 days, ten pages at most), averages 600 seconds, the player's feed 180 seconds. Old quotes can be displayed with stale status but cannot generate tags. A failed manual refresh also pauses tags until a usable fresh result arrives.

**The value of a row** (`equipment.valueOf` over `similar.similarValue`): with the item's sales read (`resale.comparableFills` cut to `WINDOW_HOURS` = 168, no durability filter: listings are always at 100%), each sale's stats are measured against the piece's as a share of every stat's roll range (`stats.STAT_RANGES`, `statDistance`: the largest share wins, so a sniper's crit, 4 wide, weighs as much as its attack, 29 wide). The value is the median of the sales within `SAME_DISTANCE` (0.1) when there are `MIN_SAME` (3), else within `SIMILAR_DISTANCE` (0.25) when there are `MIN_SIMILAR` (5), both `matched`; else of the item when there are `MIN_ITEM` (5), unmatched; the matched sales' stat span, price range and median listing-to-sale wait travel with it. Without sales, the game's average for the code from the `avg` cache, unmatched, labelled stale past its TTL. The piece's stats come off the row: `offers.readStats` takes the last `NN%` before the price as the durability and every number before it as a stat (live rows: a weapon prints attack, crit, durability; an armour piece its one stat and the durability), and `similar.rowSkills` keys them as the fills carry them. The verdicts: `dom.verdict` for the scrap side (SNIPE at `minMarginPct`, NEAR MISS below a negative threshold), FLIP when the value is `matched` and `(value − price) / price ≥ flipPct / 100` and the scraps do not hit, PASS otherwise; READING / NO QUOTE / STALE suppress every tag. `similar.listedPeers` counts the other rows of the same code within `SAME_DISTANCE` and their cheapest price. The percentile of the price among the matched sales needs eight (`resale.percentileRank`); the stat rank among listed peers needs eight too (`offers.statRanks`).

**Offer dimensions** (`offers.mjs`): `readStats` parses durability (`NN%`, the first such line) and the stat value from a row's visible lines, excluding the price line before BUY, and names its reason when it fails; `summarizeOffers` counts readable rows without reference to quotes or sales.

**The craft board** (`craftboard.mjs`): `craftCost` walks the tier's scraps and the steel fee through the asks (`quality.quote`; no price past the observed depth, the missing input named). `tierBoard` gives one row per tier: the random cost (`CRAFT_STEEL`) and the chosen-slot cost (doubled), the six slots with their odds (`RANDOM_SLOT_ODDS`) and averages, the random EV (withheld while any slot lacks an average), the best covered slot, the ROI either way, the scraps' bid value when scrapped and the loss a random craft takes when its roll is scrapped at once. `bestTier` ranks by random ROI, else by chosen ROI.

**The player's pieces** (`observed.mjs` over the feed store, read by `api.fetchOwnFeed`): `replayPieces` makes one piece of every craft (cost = the recipe at the craft day's average input prices, `averageOn`: the day, else the latest earlier day, else unknown; the steel fee the `craftSteelMode` setting names) and of every market row where the player is the buyer (cost = the money paid), then attaches each later market row where the player is the seller, or dismantle, to the latest acquisition of that item id before it that has no fate yet (a dismantle's scraps are valued at the scrap average of its day; a sale carries the listing-to-sale wait); a fate with no acquisition on record becomes a piece of source "unknown" with no cost, so its proceeds still count. `ledgerSummary` sums a window by the day things happened, in the player's local day (`localDayOf`): what was sold or scrapped (proceeds, result over the known costs, the unknown-cost count), what was crafted and bought (and how many of those already sold), and what is held, priced by `similar.similarValue` over its own fills, the same number its row would show. The replay is memoised per store read and steel mode; the bar's head prints today's result from it. The ledger reads the player id from the settings, else from the page's own-profile links (`dom.ownUserId`), and never shows a store kept for another id.

**Game facts** (`ladder.mjs`): the scrap ladder, the dismantle yield, the craft steel fee (`CRAFT_STEEL`, doubled for a chosen slot) and the random craft's slot odds, each with its provenance; `docs/GAME-FACTS.md` is the written record every number here points to.

**Preferences** (`settings.mjs`): `minMarginPct`, `flipPct`, `intervalSec`, `panel` (`none` | `market` | `craft` | `ledger`: the section open under the bar), `casesCollapsed`, `roundTrip`, the module toggles, `sellFrom`, `userId`, `craftSteelMode`. Unknown keys, including the 1.x `collapsed`, `craftCollapsed`, `craftBatch`, `craftTargetPct`, `taxPct` and `craftRecipes`, are dropped on the next save. The 1.x `craftLedger` storage entry is neither read nor removed.

## Request and account lifecycle

Single-flight identity is resource + item + account generation, never the force flag. All callers share the same active read, including manual refresh. Writes and key changes are serialized. An old-key response cannot overwrite a new account's cache. Display preference revisions do not invalidate account data; a changed key or an explicit re-save after rejection increments `authRevision` and clears account caches.

The worker remembers a rejected key across worker restarts. Saving a key explicitly clears rejection, including when the user re-saves the same corrected/renewed key. A server 429 hold is global and persisted in session storage. Transient resource failures get bounded exponential backoff with jitter; forced refresh does not bypass it.

Keys are stored in extension-local storage restricted to trusted extension contexts. Content messages only receive public preferences and `hasKey`/rejection state. Requests omit credentials, disable HTTP caching and refuse redirects. Errors redact the supplied key before returning to the page. This is local browser storage, not an encrypted password vault.

The content side keeps the fills of the last twelve items it read (`salesByCode`) so rows of other items keep their value evidence; fills freshness, errors and the read in flight are tracked per item. Fills reads are single-flight per tab: one asked for while another item's read is in flight is kept, with whether it was forced, and runs when that read finishes; reads kept while the tab was hidden run when it becomes visible again. A failed fills read is not asked again for 15 s. The rows ask for every item on the page, the grid's selected item first; the Ledger asks for the held pieces' items (eight at most) on every render, a fresh read returning at once. `SALES_CODES_KEPT` is 36, so no item on the page is evicted.

## UI lifecycle and performance

API reads stop while the tab is hidden, and so does rendering: a setting saved from a hidden tab shows once the tab is visible. The scrap book and the averages are read whenever the rows are on screen; the steel book with the Craft tab open; the player's feed store is polled whenever the bar is on screen and the player id is known, whatever tab is open, so a sale shows in the head within a minute. No notification, sound or badge: a number that updates is display, a ping is not. Rendering uses scoped mutation roots, filters extension-owned mutations and coalesces native mutation bursts with a 100 ms scheduler. Unchanged markup is not written again, and an age label ("12s ago") changing by itself does not count as changed markup; `clock()` keeps ages current. A rewrite keeps keyboard focus on the same control, identified by its action or field together with the code, id, type, tab, tier or window it carries. The bar (`panel.mountBar`) sits before the market's tax notice, else before the section holding the item grid (`dom.marketAnchor`), and stays put while only the extension's own nodes sit between it and its anchor; its head is `app.mjs`'s, its body is rendered by `equipment.renderMarket` or `craftdesk.render` for the open tab, or hidden.

Offer scans are scoped: rows are looked for inside the list container found by the previous scan, with a full-document scan when that container is gone, finds nothing, or every 30 s. `createRowCache` keeps each row's parsed lines, price, frame and border colour; the layout-forcing `innerText` is read again only when the row's native text changes, and the frame colour only on a full scan (a new cache epoch), so a theme change is still picked up. Per-row annotation HTML is rebuilt only when its memo key (tag, quote time, thresholds, fills snapshot, value, stat rank, Details state) changes. Only the Details button and the Details text catch a click; the rest of the line is the row's, in the click handler as in the stylesheet.

A light five-second heartbeat checks preference revisions, URL changes and freshness transitions. A 30-second discovery fallback catches replaced SPA containers or newly opened dialogs outside observed roots. This deliberately avoids patching the game's history or global JavaScript.

Dispose disconnects the observer, cancels timers, removes extension UI (the bar, the row lines, the case strip, the trip line) and restores picker visibility. The content bootstrap handles ordinary unload; persisted back/forward-cache pages keep their instance. A second content-script injection is stopped by the original `window.__scrapSniper` marker.

## Tests and extension safety

Run `npm run check`. Unit tests cover models (the stat-matched value and its 7-day window, the live row layouts, the feed walk's stops and the store's merge and coverage, the pieces' replay and the day's result, the craft board, the feed walk and its cutoffs, the replay, the resale thresholds, depth), malformed envelopes, pagination, missing headers, escaped text. Controller tests use injected storage, fetch and clock for races, cooldowns and the feed cache. jsdom tests cover SPA navigation, mutation storms, hidden tabs, settings updates, duplicate mounting, the Details control, the bar's tabs, the craft board, the ledger and cleanup. They do not prove real Chrome layout, extension permission behavior, live API compatibility or the live page's row text; `scripts/screenshots.mjs` renders the synthetic fixture in headless Chromium for screenshots and the loader benchmark.

The strict JS/TypeScript check covers `quality`, `settings`, `format`, `items`, `ladder`, `stats`, `resale`, `offers`, `craft`, `craftdata`, `craftboard`, `similar` and `observed`. Expand this list as additional modules gain types; do not represent it as whole-project TypeScript coverage. ESLint checks all extension code and scripts. The manifest validator walks local module imports and ensures privileged modules are not web-accessible.

When adding a feature, start with a pure model and a fixture, add a controller resource only if necessary, then mount it through `app.mjs`. Never add the API key to the content state, patch the page's `fetch`, or call a transaction mutation endpoint.
